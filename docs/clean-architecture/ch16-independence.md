# 第 16 章 独立性（Independence）

## 本章讲什么

好架构要支撑四种独立：**用例独立**（架构一眼看出系统干什么——"尖叫"）、
**开发独立**（团队并行不踩脚）、**部署独立**（组件可各自部署）、
**运维独立**（用例可独立扩缩容）。共同点：独立性是"将来需要时拆得开"，
不是"现在就拆"。边界有三级形态（源码级/部署级/服务级），好架构让系统能沿
三级往上迁移，而不是第一天站在最贵那级。

压轴：**重复是个假象（The Fallacy of Duplication）**——
- 真重复：永远因同一理由同时变化 → 消除；
- 假重复：今天长得像、将来因不同理由各自演化 → **必须容忍**。
  误消假重复 = 把变化节奏不同的东西焊死，日后每次分叉往共享代码塞 if，越改越丑。

## 对照本项目

四种独立：用例独立及格（目录喊业务）；开发独立已预置（三端 service 互不 import）；
部署独立 = 单二进制（CCP 角正解，非欠账）；运维独立 = HMD/HPD 分离留了读模型
单独扩容的口子。三级边界各有样本且大头站最便宜一级。

真假重复过堂：

1. **三端 auth service**——行为者不同、登录方式已分化。假重复，分开正确；
2. **listingprojection 三套 mapper**——三端各自视角。假重复；
3. **HMD 集中式/分散式两族**——结构规则不同。假重复（第 9 章 LSP 已论证）；
4. **publish 六子 service 骨架**——"scope 校验→调 domain→投影→日志"这个流程是
   **真重复**（日志改版、outbox 迁移时六处一起变）。现状是聪明的中间态：
   确定一起变的片段已抽共享（resolveHmdMutation、rollbackCreateFailure），
   可能分叉的骨架留在各文件。**共享确定的，容忍不确定的。**

## 讨论沉淀（2026-07）

### AI 协作警告（本章最重要的实践输出）

**CC/GPT 有强烈的消重复本能**——看到三段相似代码就想抽公共函数，而它不知道
三端是有意分开的。防法：写进 CLAUDE.md / 重构指令约束——
"三端相似代码是按行为者有意分开的，禁止跨端抽公共"。
真假重复的判断需要业务预判，这是 AI 没有、架构师有的信息。

### session 思考题结论：机制与载荷分开判

- **机制**（opaque token、Redis 存取、TTL、防伪）：变化理由是安全和技术，
  三端必然一起变——真重复，共用一套正确；
- **载荷**（Principal 字段）：RoleCodes/PermissionCodes 只有 admin 消费，
  Phone 是 miniapp/publish 的——各端行为者往里加的，轻微 CRP 违例，现在无所谓。
  **分叉信号**：端侧字段开始各自膨胀（admin 加部门/数据范围、miniapp 加会员等级）时，
  手术 = Store 机制共用，载荷拆三端各自 struct（Principal 只留真公共字段）。

"机制与载荷分离"与"错误命名/错误翻译分离""数据/投影分离"是同一个手型，
本项目第三次出现。
