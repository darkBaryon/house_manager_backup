# 第 17 章 边界：画线的艺术（Boundaries: Drawing Lines）

## 本章讲什么

边界 = 把软件元素分开、让两侧不需要知道对方细节的线。画线判据：
**线画在变更轴上——两侧应以不同原因、不同速率变化**。业务规则与细节之间永远值得画。

结构：系统分成核心业务逻辑组件 + 插件组件，**修改源码依赖，让插件依赖核心**
（DIP/SAP 应用，箭头由底层具体实现指向高层抽象）。插件式架构 = 一面变更无法
逾越的防火墙：GUI/DB 怎么变都影响不到业务规则。FitNesse 故事：先画数据访问边界、
用内存实现顶着开发，MySQL 决策被推迟到"永远"——边界买到的不只是能换，是可以先不选。

## 对照本项目

插件视角全景（箭头都指向业务规则，谁指向你谁就是你的插件）：

```text
                    ┌─ Gin handler 插件（随时整体可换）
service + domain ←──┼─ Mongo repository 插件
（业务规则本体）      ├─ Redis 插件（cache.Client 后）
                    └─ Python AI 插件（AIResponder 后）
```

测试体系是验收证明：普通 `go test ./...` 不依赖真实 Mongo/Redis——插件拔得下来。

**Go↔Python 线的复盘**（本项目画得最重也最准的一条）：开发时的真实决策——会话、
消息、上下文放哪侧？选择"Go 是 owner，Python 只做推理"。论证：**"对话状态怎么管"
是业务规则，"用哪个模型怎么推理"是细节**；且若 Python 全包，同一套数据逻辑要用
py 重写一遍（真重复的跨语言版）。推论成立：Python 侧随便换框架/模型/重写，
会话数据和业务流程纹丝不动。Py 的提示词/模板将来可能需要自己的库——
"即便需要也是以后的事情" = 最大化未做决策的实操。

## 讨论沉淀（2026-07）

### 足迹思考题完整答案：repo 提供能力，svc 拥有策略

需求"按天聚合、去重、只保留 30 天"的正确分工：

- **30 天筛选**：查询是 repo 的活（有索引；svc 自己筛 = 全量捞内存，数据一多就炸）。
  但切法：repo 方法是 `ListSince(ctx, userID, t time.Time)`——参数是时间点不是"30 天"；
  `30` 住 svc/config。反面 `ListLast30Days()` = 策略泄进机制层，改 60 天要动 repository；
- **去重**：不要偷偷改 Add 的语义（签名没变契约变了 = LSP 违例）——新增语义诚实的
  `Upsert`/`Touch`。且 svc"先查再加"有并发窗口，可靠去重靠 repo 用 unique index +
  upsert 原子完成。"要不要去重"是策略（svc），"怎么原子地去"是能力（repo）；
- **保留期删除**：Mongo TTL index 一行解决，但意味着策略数字刻进数据库——
  可以选，记账：这是策略对机制层的有意泄漏。

**边界画对的标志不是"改动只落一层"，而是两层的 diff 各说各的方言**：
svc 的 diff 全是业务词（30 天、去重规则），repo 的 diff 全是机制词（索引、upsert）。
穿帮信号：repo 里出现业务数字，或 svc 里出现 Mongo 查询语法。

### 依赖箭头（因）与变更免疫（果）

书的小结讲箭头方向（结构），思考题验证变更落点（行为）——同一件事的因果：
**箭头指向核心 ⟹ 变更被边界挡住、两侧各说方言。小结教施工，思考题教验收，
验收方法 = "这个需求来了，diff 落在哪"。**

实证：`service/miniapp/history/service.go` 声明消费侧 `historyRepository` 接口
（箭头已反转）。附带发现：service.go 里作者自留 TODO——"replace full-load plus
in-memory filtering/paging with repository methods"，正是"能力错放在策略层"的
活体标本，方向与本章答案一致。

### 边界的价格表

每条线 = 接口 + 数据转换 + 认知负担。本项目的层次：AI 边界画全（变化最猛，值得）、
Mongo 边界画一半（操作隔离了、类型渗了——有意识赌注）、三端 service 之间只有包边界（够用）。
