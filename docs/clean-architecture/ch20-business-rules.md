# 第 20 章 业务逻辑（Business Rules）

## 本章讲什么

"住在最高处的业务规则"拆开是两种东西，级别还不一样：

- **实体（Entity）= 关键业务规则 + 关键业务数据**。判定口诀：**拔掉电脑，这条规则
  还在不在？**在，就是实体规则（银行的计息规则，算盘时代照样执行）。实体不知道
  数据库、界面、也不知道会被哪个应用使用；
- **用例（Use Case）= 应用特有的业务规则**：描述本系统被使用的方式——什么输入、
  什么步骤、何时调用实体的规则、什么输出。

**实体比用例级别更高**（易记反）：用例描述"本应用怎么用实体"，离具体应用更近；
实体可被 N 个应用复用，离一切都远。依赖方向永远是用例 → 实体。

**请求和响应模型**：用例的输入输出应是朴素数据结构——不引用 HTTP/框架，
**也不要偷懒把实体直接传出去**（实体随业务变、响应随界面变，绑一起 = 假重复合并事故）。

## 对照本项目

拔电脑口诀扫 publish 链路，各归其位：

- "房间属于楼栋、楼栋属于项目、集中式分散式结构不同"——纸质台账时代照样成立。
  **实体规则** → domain/hmd ✓
- "发房前校验 scope、写入后刷投影、失败补偿回滚"——本系统的操作规程。
  **用例规则** → service/publish ✓
- 依赖方向 service→domain 单向 ✓。**domain/ ≈ 实体层、service/ ≈ 用例层，二分成立。**
- N 应用共享实体的实景：将来 admin 代房东改房源时，admin 用例与 publish 用例
  共享 domain/hmd（端侧策略归各用例，结构规则归实体）。

**实体是"拆开的"**：书的实体 = 数据+规则打包一个对象（Loan.calculateInterest()）；
本项目数据在 model/hmd（纯 struct）、规则在 domain/hmd（函数）——Go 主流的
贫血风格。用论证体系检验：级别对、方向对、共同闭包对——**架构约束全部满足，
打包风格之争，不是对错之争，不改**。

请求响应模型对账：
- 模范：SendInput/SendResult、CreateBuildingInput（朴素 struct 零框架词汇）；
  listingview.Item 纯展示数据（PriceText/FloorText——存储层根本没有的字段），
  与存储模型彻底两套；handler 侧 dto.go（createRequest/response + toResponse）；
- 欠账：publish 用例返回值直接是 *hmdmodel.HmdBuilding——**Mongo 模型穿过用例边界**，
  一个 struct 打三份工（存储 schema/领域数据/用例输出）。潜在事故：model 加内部字段
  （如 UpdatedBy），每个 toResponse 要"记得别暴露"——防线从结构保证退化为人人记得住。
  判决：handler DTO 已挡住线上契约，全面合规的映射税不值得付，记账。
  **映射层按需生长，不按教条预建**（miniapp 的 listingview 示范了何时值得付：
  输出形状真分化时那层自然出现）。

## 讨论沉淀（2026-07）

### 接口不是每条层间边界都要——方向冲突判据

**接口只在一种边上必需：控制流方向与期望依赖方向相反的边。**

- 同向（handler 调 service：控制流向内，依赖也该向内）→ 直接 import 具体类型，
  不需要接口。外圈本来就该认识内圈；
- 反向（service 调 Mongo/AI：控制流向外，依赖不许向外）→ 接口是唯一解法——
  它不是"解耦的美德"，是**让两个矛盾的方向同时成立的机械装置**，没有矛盾的地方
  不需要装置。

本项目两种都有：service/chat 的三个 repo 接口 = 必需品；
handler/building 的 `type Service interface` = 可选品（买测试便利，不加也合规）。
**接口跟着"方向冲突"走，不跟着"层的数量"走**——每层都隔接口是把机械装置当装饰品。

### "实体和响应独立"的确切含义

不是字段不许长得像，是**不让同一个 struct 打两份工**：每层的形状由各自的变化理由
驱动，不共享定义。前端改字段名只动 dto 的 json tag；业务加字段后要不要暴露给 API
是 dto 层的显式决定（toResponse 加不加那行），不是自动泄漏。反面：
`c.JSON(200, building)` 直接序列化 model = Mongo 字段名成为 API 契约。

### 检验题存档

"session 空闲超时自动开新会话"——**用例规则**：超时时长来自
AI_CHAT_SESSION_IDLE_TIMEOUT 配置，是本应用的运营参数；拔掉电脑，
"对话隔久了算新对话"并非业务界的永恒规则。
