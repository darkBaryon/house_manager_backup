# 第 12 章 组件（Components）

## 本章讲什么

**组件 = 可以独立部署/发布的最小单位。**各语言的实体形态：jar、DLL、gem、npm 包。
判断标准很物理：能被单独打包、单独标版本号、单独发给别人用。本章大半是历史课
（重定位技术、链接器的出现让"编译好的代码块随意组合"成为可能），结论记一句即可：
组件化的本质是**独立编译 + 独立版本 + 随意组合**。

## 对照本项目

Go 的对应物分两级：

- **严格意义的组件 = module**（一个 go.mod 管辖），有版本 tag，能被 `go get`；
- **口语的"组件" = package**，独立编译但没有独立版本，跟仓库一起进退——只是候选者。

拿这把尺子量出的全景图：

```text
你写的组件：   house-manager Go 服务（整个仓库 = 1 个组件）
              Python AI 服务
              shared-docs（submodule，独立版本的文档组件）
别人写的组件： MongoDB、Redis（部署级）；go.mod 里每一行依赖（代码级）
还不是组件：   internal/ 和 pkg/ 的所有包（候选者）
              wire/（永远不够格：只属于本次组装，无复用价值）
              config YAML（不是代码，是部署时喂给组件的参数）
```

## 讨论沉淀（2026-07）

### 三级阶梯：包 → 库组件 → 服务

```text
包 (package)    同进程，同仓库，一起发版          ← pkg/logger 在这
  ↓ 独立 go.mod + 版本 tag
库组件 (module)  同进程，独立发版，别人 go get     
  ↓ 进程边界 + 网络协议
服务 (service)   独立进程，独立部署，HTTP/RPC     ← Python 服务在这
```

每升一级，耦合更松、运维更贵。**服务只是"边界恰好是网络"的组件**（第 27 章观点），
微服务不是架构，是组件边界的实现选项之一。边界的重量应与两侧差异成正比：
差异只是"变化快慢"，包边界够；差异到"语言都不同、发布节奏独立"（Python 服务），
才值得付网络边界的税。

### 第三方依赖恰恰是组件的主要形态

"第三方不归我们管"错了一半：代码不归你管，**关系归你管**，且已在管——

1. **版本钉住**：go.sum、Mongo 版本，升不升、何时升是你的决策；
2. **隔离深度**（最重要）：第三方类型允许渗透多深？对比项目里两个极端——
   `bson.ObjectID` 渗进了 domain 接口签名（mongo-driver 类型进了最内圈），
   `AIResponder` 输入输出全是自定义类型（pythonchat 什么都没漏进来）。
   渗透多深应该是**有意识的决定**；
3. **替换预案**：Mongo 藏在 repository 后、AI 藏在 port 后——为"换掉它"买的保险。

### 判定练习存档

- wire/：非组件，且是全项目最没资格成为组件的代码（只属于本次组装）；
- config YAML：非组件，是部署参数（同一个二进制组件，不同环境喂不同 YAML）；
- MongoDB：**是组件**（独立部署、独立版本、可插拔替换），只是作者不是你；
- "放在 pkg/ 目录" ≠ "是组件"，"能独立发版"才是。
