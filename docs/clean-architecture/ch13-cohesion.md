# 第 13 章 组件聚合（Component Cohesion）

## 本章讲什么

三条原则决定"一个组件里该装什么"，且互相打架：

- **REP 复用/发布等价原则**：复用的最小单位 = 发布的最小单位。想让别人复用，
  就得给版本号和发布节奏；组件里装的东西必须"值得一起发布"。
- **CCP 共同闭包原则**：因相同原因、相同时刻变化的类聚在一起（SRP 的组件版）。
  目标：一个需求的改动落在一个组件里。
- **CRP 共同复用原则**：不强迫使用者依赖用不到的东西（ISP 的组件版）。刀法是做减法。

**张力三角**：REP 和 CCP 往里装，CRP 往外拆，三者不可兼得。唯一普适建议：
**项目位置随年龄漂移**——早期站 CCP 角（可维护性优先，东西放一起），
有了真实复用者才向 REP/CRP 漂。

## 对照本项目

整个仓库 = 单 module，internal/ 三十几个包绑在一起发布——**标准的 CCP 角站位**，
对单人、快迭代、无第二消费者的项目是教科书推荐位置。"pkg 理论上可拆但没拆"的
直觉翻译过来就是：没有复用者之前 REP 收益为零，拆分税白付。

shared-docs submodule 是唯一站 REP 角的东西：文档有多个消费者（Python、前端），
换来的税是每次改接口要跨两个仓库提交 + bump submodule 指针——REP 和 CCP
打架的具体形状，选了 REP 就付 CCP 的税。

## 讨论沉淀（2026-07）

### 拆成独立 module 的具体成本（四步舞）

拆出去之后，"同仓库改一行随手提交"变成：
① 在组件仓库改代码提交 → ② 打新 tag → ③ 主仓库 go get 新版本 → ④ 提交 go.mod/go.sum。
每次变更多付三步，跨两个仓库。收益：别人能用、可以停在旧版本。

### errcode vs logger 思想实验

判据 = CCP 问的那个问题：**它因什么变、跟谁一起变？**

- **errcode 拆了会痛**：`RoomNotFound = New(20001, ...)` 这种内容随业务变
  （每个新模块加一批码），变化节奏 = 业务开发节奏，和 internal/ 是共同闭包。
  硬拆 = 每个新功能跳一遍四步舞；且对外无复用价值（错误码是本项目的业务契约）。
  REP 收益零、CCP 代价满，纯亏。
- **logger 拆了无所谓**：通用基础设施，因技术偏好变、几乎不变，和业务不构成
  共同闭包；第二个 Go 项目若想复用还能兑现 REP。

**万能判据：跟着业务一起变的，留在业务旁边（CCP）；不跟业务变、可能被第二个
项目用的，才有资格独立发版（REP）。**

### 现实中触发拆分的四种动机

1. **第二个消费者出现**（最常见最正当）：第二个项目要共享代码，只有复制或拆 module 两条路；
2. **第二个团队出现**：别人需要"停在 v1.4 不跟你升"的权利，版本号是团队间的解耦合同；
3. **强制解耦**：独立 module 无法反向 import 主项目，物理隔离（如逼 chat 保持纯净）；
4. **发布节奏确实不同**：shared-docs 即此类。

本项目今天四条全不占——**没有任何理由拆，一个都没有**。动机决定要不要拆（现在：不拆），
判据决定拆哪些（将来：logger/cache/session 够格，errcode 不够格）。
