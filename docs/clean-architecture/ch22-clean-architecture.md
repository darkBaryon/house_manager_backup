# 第 22 章 整洁架构（The Clean Architecture）

## 本章讲什么

著名的四圈图 + 一条依赖规则（Dependency Rule）：

```text
圈1 实体（最内）← 圈2 用例 ← 圈3 接口适配器 ← 圈4 框架与驱动（最外）
铁律：源码依赖只准指向内侧。内圈不知道外圈的任何名字。
```

配套细则：跨边界的控制流向外时用接口反转（右下角 Controller→InputPort←Interactor
→OutputPort←Presenter 小图）；跨边界的数据必须是朴素结构，不许把外圈格式
（数据库行、HTTP 对象）递进内圈。

本章开篇 Martin 自己交代：六边形架构（Ports & Adapters）、洋葱架构、BCE 等
核心主张全部相同，同心圆是给这一家族出的统一合影——AIResponder 这个装置，
六边形叫 port，洋葱叫内层接口，Martin 叫 boundary，同一个东西三个名字。

## 全项目逐圈对账

- **圈 4（框架与驱动）**：Gin 本体、mongo-driver、go-redis、Mongo/Redis/Python
  三个外部进程、config YAML、wire/（组装点，豁免铁律的唯一住户）；
- **圈 3（接口适配器）**：handler/v1/*（控制器 + dto.go 的 presenter 职能）、
  middleware/、repository/*（数据库网关）、integration/pythonchat（外部服务网关）、
  pkg/response、app/。handler 与 repository 同圈——第 19 章"拱形"的官方版本；
- **圈 2（用例）**：service/* 全家 + 各自 Input/Output types；
- **圈 1（实体）**：domain/hmd、domain/publishaccess、model/*（关键业务数据）。

**对账发现**：domain/listingprojection 住在 domain/ 目录，但按定义是**圈 2 居民**
（"本系统要维护三个读模型"是本应用的规程，拔掉电脑不存在投影）。依赖方向全对，
不算违规——目录名与圈层身份不一致，知道即可，Go 按 import 算不按文件夹算。

### 边界杂质终表（全书讨论归档）

| 杂质 | 违规形态 | 判决 |
|---|---|---|
| bson.ObjectID | 圈 4 类型出现在圈 1/2 签名 | 有意识赌注，保持；下个项目第一天用自有 ID 类型 |

除此三处，全项目 import 边无一条从内指向外。**成绩单：不是无暇，而是每道疤都有名字。**

## 讨论沉淀（2026-07）

### 全书可执行内核（四句压缩版）

> **按变更轴切组件 → 按 I/O 距离排级别 → import 只准向内、调用向外处插接口 →
> 最外圈一个组装点拼起来。**

其余章节全是这四句的论证、变体和历史脚注。

### 条件反射："调用"和"依赖"永远分开说

谁调用谁是运行时事实，改不了也不用改；谁 import 谁是源码的选择，铁律只约束它。
第 11 章到第 22 章的一切玄机都在这两个词的分离里。

### 为什么存在别的架构——同心圆是力学原理，不是建筑样式

同心圆只回答一个问题："怎么安排依赖让业务规则的变更便宜"。其他架构样式主攻别的轴：
微服务=组织与运维轴（几百人并行、独立扩缩容），事件驱动=性能时序轴，
CQRS/事件溯源=数据轴，流水线=计算形状轴。这些轴与依赖纪律**正交**、可叠加——
做得好的微服务，每个服务内部照样画同心圆。

本项目即活的叠加样本：宏观"单体+外挂服务"（部署形状）+ HMD/HPD 读写分离
（CQRS 轻量版）+ 每块内部同心圆纪律。三种"架构"同时成立，因为回答的是三个问题。

类比：建筑样式千差万别（教堂/民居/摩天楼），但都服从静力学（承重不能挂在装饰上）。
**任何想要业务可变性的架构，最后都会重新发明"策略不依赖细节"**；不需要这性质的
系统（一次性脚本、性能压倒一切的路径）可以光明正大不服从——第 15 章的豁免条款。

架构师的完整工作因此两段式：先按真实约束选样式（无标准答案的权衡），
再在样式内部执行依赖纪律（同心圆几乎就是标准答案）。本书只教后半段——
不是缺陷，是边界。

### 一句话总结这本书

**这本书讲的就是依赖规则，和执行它的一整套机械（接口反转、边界、组件、组装点），
外加一门"何时值得付钱"的判断学（变更轴、引信、价目表）。**前两样书里写满了，
第三样只能靠案例喂。
