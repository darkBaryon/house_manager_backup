# 第 9 章 LSP：里氏替换原则

## 这章讲什么

里氏替换原则源自 Barbara Liskov 1988 年对"子类型"的定义，通俗版是：

> 凡是使用父类型的地方，换成任何一个子类型，程序的行为都不应该出错或变得不正常。

经典反例是"正方形/长方形"问题：数学上正方形是长方形，但如果让 `Square` 继承
`Rectangle`，调用方写下 `r.setW(5); r.setH(2); assert(r.area() == 10)` 时，
传进来一个 `Square` 就会断言失败（改宽会同时改高）。**继承关系成立与否，不取决于
概念上"是不是"，而取决于调用方的预期是否被遵守。**子类型必须履行父类型的契约。

这章的重要升级是：Martin 把 LSP 从"继承的准则"扩展成了**架构级原则**。凡是有
"一个接口、多个实现"的地方——REST 服务的多个提供方、同一消息格式的多个消费者、
插件体系——都受 LSP 约束。他举了个出租车调度的例子：所有车队都按统一的 URI 格式
接受调度，某家公司的司机不遵守约定，系统就得到处塞 `if (driver == "ACME")` 这种
特判。**LSP 被破坏的气味，就是调用方开始出现针对具体实现的 if/switch。**

## 对照本项目

Go 没有继承，但接口的隐式实现让 LSP 无处不在。

**1. `AIResponder` 的行为契约。**
`service/chat.Service` 对这个接口的预期不只是方法签名，还包括隐含契约：
超时会返回 error 而不是永远挂起、返回的 `AIRespondOutput` 字段语义稳定、
不会偷偷修改 Go 侧的会话状态。README 的约束"Python 不写 Go 的 Mongo chat
collection"正是一条**行为契约**——它不体现在任何函数签名里，却是替换实现时
必须遵守的。将来若有第二个 responder 实现，签名对了但背着用例直接写库，
类型系统不会报错，LSP 却已经被破坏了。

**2. 测试替身也是"子类型"。**
`internal/service/chat/service_test.go` 里用假的 responder 来测试用例逻辑。
测试替身能成立的前提，恰恰是真假实现都遵守同一份契约——mock 返回了真实现
永远不会返回的东西，测试就在验证一个不存在的世界。写 mock 时时刻问一句
"真实现会这样吗"，就是在做 LSP 检查。

**3. 集中式/分散式房源。**
`domain/hmd` 里集中式项目（centralized）和分散式小区（decentralized）是两套
类型（`hmd_centralized_*.go` / `hmd_decentralized_*.go`）。项目**没有**强行给
它们抽一个共同的"房源"父类型，因为两者的结构规则（项目→楼栋→房型→房间 vs
小区→房间）根本不同，硬抽公共接口，调用方迟早要写 `if 集中式` 的特判——
那正是 LSP 破坏的气味。**不该统一的东西不统一，也是对 LSP 的尊重。**

## 一个容易犯的错

把 LSP 理解成"编译器能查的事"。恰恰相反：签名兼容编译器已经管了，LSP 管的是
签名之外的部分——错误语义、副作用、性能预期、幂等性。这些只能靠文档（如本项目
README 的约束清单）和针对契约的测试来守住。
