# 第 9 章 LSP：里氏替换原则

## 这章讲什么

里氏替换原则源自 Barbara Liskov 1988 年对"子类型"的定义，通俗版是：

> 凡是使用父类型的地方，换成任何一个子类型，程序的行为都不应该出错或变得不正常。

经典反例是"正方形/长方形"问题：数学上正方形是长方形，但如果让 `Square` 继承
`Rectangle`，调用方写下 `r.setW(5); r.setH(2); assert(r.area() == 10)` 时，
传进来一个 `Square` 就会断言失败（改宽会同时改高）。**继承关系成立与否，不取决于
概念上"是不是"，而取决于调用方的预期是否被遵守。**子类型必须履行父类型的契约。

这章的重要升级是：Martin 把 LSP 从"继承的准则"扩展成了**架构级原则**。凡是有
"一个接口、多个实现"的地方——REST 服务的多个提供方、同一消息格式的多个消费者、
插件体系——都受 LSP 约束。他举了个出租车调度的例子：所有车队都按统一的 URI 格式
接受调度，某家公司的司机不遵守约定，系统就得到处塞 `if (driver == "ACME")` 这种
特判。**LSP 被破坏的气味，就是调用方开始出现针对具体实现的 if/switch。**

## 对照本项目

Go 没有继承，但接口的隐式实现让 LSP 无处不在。

**1. `AIResponder` 的行为契约。**
`service/chat.Service` 对这个接口的预期不只是方法签名，还包括隐含契约：
超时会返回 error 而不是永远挂起、返回的 `AIRespondOutput` 字段语义稳定、
不会偷偷修改 Go 侧的会话状态。README 的约束"Python 不写 Go 的 Mongo chat
collection"正是一条**行为契约**——它不体现在任何函数签名里，却是替换实现时
必须遵守的。将来若有第二个 responder 实现，签名对了但背着用例直接写库，
类型系统不会报错，LSP 却已经被破坏了。

**2. 测试替身也是"子类型"。**
`internal/service/chat/service_test.go` 里用假的 responder 来测试用例逻辑。
测试替身能成立的前提，恰恰是真假实现都遵守同一份契约——mock 返回了真实现
永远不会返回的东西，测试就在验证一个不存在的世界。写 mock 时时刻问一句
"真实现会这样吗"，就是在做 LSP 检查。

**3. 集中式/分散式房源。**
`domain/hmd` 里集中式项目（centralized）和分散式小区（decentralized）是两套
类型（`hmd_centralized_*.go` / `hmd_decentralized_*.go`）。项目**没有**强行给
它们抽一个共同的"房源"父类型，因为两者的结构规则（项目→楼栋→房型→房间 vs
小区→房间）根本不同，硬抽公共接口，调用方迟早要写 `if 集中式` 的特判——
那正是 LSP 破坏的气味。**不该统一的东西不统一，也是对 LSP 的尊重。**

## 一个容易犯的错

把 LSP 理解成"编译器能查的事"。恰恰相反：签名兼容编译器已经管了，LSP 管的是
签名之外的部分——错误语义、副作用、性能预期、幂等性。这些只能靠文档（如本项目
README 的约束清单）和针对契约的测试来守住。

## 讨论沉淀（2026-07）

### `projector.Refresh` 的幂等契约三问（讨论中已解答）

`listingprojection` 里 projector 接口签名只有 `Refresh(ctx, change) error` 一行，
但注释里写着签名体现不出来的关键词：**幂等**。三问串成一条线：

1. **为什么幂等必须是隐性契约？** `Service.Apply` 循环依次刷三个 projector，
   第二个失败时第一个已刷完，而整个写请求失败、房东会重试——重试时第一个 projector
   会被**再刷一遍**。
2. **不幂等的第四个 projector 会炸出什么？** 如果它的 Refresh 是"追加一条"或
   "计数器 +1"而不是"按 ID 重查覆盖写"，重试场景下就是 +2、+3、+4——数据静默腐坏。
3. **和 LSP 什么关系？** 编译器不拦它（"这不是语法错误，是逻辑错误"）——
   **这正是 LSP 作为原则存在的全部理由**：接口契约 = 签名 + 行为约定，编译器只查
   得了签名那一半。"能替换进切片但行为不对"，就是 LSP 违例的定义本身。
   正方形/长方形是它的继承版，不幂等 projector 是它的接口版，同一个病。

落地两条：**契约写下来**（projector 注释的"幂等"、README 的 chat 军规都是契约条款，
这个习惯要保持）；**契约靠测试守**——通用契约测试"同一 change 调两次 Refresh，
断言终态相同"，新 projector 挂上去跑，不幂等当场现形。

### 编译器帮得上忙的只有一半

| 原则 | 违例可否被工具查出 | 怎么查 |
|---|---|---|
| ISP / DIP | 可以 | 体现在 import 关系上（depguard 等 lint 可强制） |
| SRP / OCP / LSP | 不可以 | 编译通过、测试通过，痛在未来的变更/替换时 |

这就是架构评审看依赖方向、契约、变化轴而不是"能不能跑"的原因；也是"AI 能保证
编译通过，但契约齐不齐、轴押得对不对仍是人的活"的出处。

### "盲用"判断口诀：不该统一的不统一

集中式/分散式没抽公共"房源"接口是**对的**。判断标准不是"概念上都是房源"，而是
**调用方能否盲用**——拿到接口不问"你是哪种"就能正确使用。对照 `ports.go`：
`ListCentralizedRoomsByProject` / `ListCentralizedRoomsByBuilding` 两个维度 vs
`ListDecentralizedRoomsByCommunity` 一个维度，方法集合和返回类型都不同，无法盲用。
硬抽统一接口的下场：要么签名空泛到丢光类型安全，要么分散式被迫实现对它无意义的
`ListByBuilding`（返回空还是报错？调用方开始猜 = LSP 破产），要么调用方到处
`if 集中式 else 分散式`——那正是 LSP 被破坏的标准气味。
**"概念上像"不是抽接口的理由，"调用方能盲用"才是。**
