# 第 18 章 边界剖析（Boundary Anatomy）

## 本章讲什么

同一条逻辑边界，运行时的物理形态是一张从轻到重的光谱：

1. **源码级（单体内）**：边界只存在于包/接口组织里，跨越 = 函数调用（纳秒、必达）。
   最便宜，也最容易被悄悄穿透（纪律是君子协定级）；
2. **部署组件（DLL/jar）**：独立发布的编译产物插进同一进程（类比：游戏 Mod——
   jar 扔进 mods/ 目录，不重编游戏本体）。**Go 砍掉了这一级**（静态链接，全部源码
   编成单个二进制）——这也是 Go 项目想要部署独立性时往往直接跳到服务级的隐性原因；
3. **线程**：不是架构边界，只是执行调度方式（goroutine 同理：outbox 改异步改变时序，
   不改变"投影是 HMD 插件"的依赖结构）；
4. **本地进程**：独立地址空间、同机、socket 通信——序列化 + 系统调用，成本毫秒级、
   可能失败。低层进程是高层进程的插件；
5. **服务**：不假设同机，一切过网络。两条纪律：默认网络又慢又不可靠（超时/重试/
   粗粒度接口）；依赖规则不变——低层服务仍是高层服务的插件。

小结：大多数系统**混用**多种形态，不是"单体 vs 微服务"二选一。

## 地基补课：进程与 I/O

进程 = 正在运行的程序 + 它的专属隔离内存（`ps aux` 每一行）。进程间内存隔离，
交换数据只能走 OS 通道（同机也要 socket）。本地联调时本项目就是四个进程：
Go、Python、Mongo（隧道）、Redis（隧道）。

**真正要紧的只有两档：同进程（函数调用：快、必达）vs 跨进程（网络：慢一万倍、会失败）。**
跨进程调用必须配超时、考虑失败、粗粒度——`AI_CHAT_RESPOND_TIMEOUT` 配置、
"一次 respond 带全上下文"的设计即正确对待。

## 对照本项目：边界配置单

| 边界 | 物理形态 | 级别 |
|---|---|---|
| handler↔service↔domain↔repository | 源码级（包+接口） | 最轻 |
| goroutine / 将来的 outbox worker | 线程级（非边界） | — |
| Go↔Python（开发，127.0.0.1:5000） | 本地进程级，**按服务级协议建** | 中 |
| Go↔Python / Mongo / Redis（生产） | 服务级 | 最重 |

## 讨论沉淀（2026-07）

- 同一逻辑动作跨多级物理形态：`service/chat` 调 `AIResponder.Respond` 是接口方法
  调用（便宜端），穿过 pythonchat.Client 变成 HTTP POST（昂贵端）——
  逻辑边界与物理形态分离的活例；
- **Go↔Python 用 HTTP 说话 = 免费升级通道**：今天是本地进程（同机），明天 Python
  搬去独立服务器自动变服务级，代码零改动——④和⑤通信方式相同，差的只是电缆长度。
  最优策略：**能用轻边界绝不用重的，但轻边界的纪律按重边界的标准守**
  （单体内依赖方向不乱、跨进程协议按跨网络设计），系统保有随规模升级边界厚度的
  选择权。
