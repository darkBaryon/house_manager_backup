# 第 19 章 策略与层次（Policy and Level）

## 本章讲什么

软件系统 = 一组策略的陈述（输入如何转换成输出的规则集）。架构工作 = 按变化的
理由和时机给策略分组，再安排依赖方向。

**级别的精确定义：一个策略的级别 = 它到系统输入/输出的距离。**离 I/O 越远级别越高。
不依赖调用关系、不依赖目录结构，客观可量。

"输入/输出"指**数据穿过进程边界的一切接触点**（给进程画个圈，穿圈处即 I/O）——
不只是用户界面：HTTP 口、数据库口、外部服务口都是。**方向不重要**（Mongo 既是
输入也是输出），"是否在伺候圈口"才重要——所以 handler 和 repository 级别相同、
同属最外圈。

加密程序案例：读字符/写字符（贴 I/O，最低级）vs 转换算法（最远，最高级）。
坏版本 = 加密函数直接调 readChar/writeChar：输入设备一换（键盘→文件→网络），
算法所在的包被反复打开——**程序里唯一值钱且从未变过需求的代码，被打扰得最勤**。
好版本 = 加密策略声明 CharReader/CharWriter 接口，设备作为插件实现——
`translate()` 从此住无人打扰的顶层。

数据流 ≠ 依赖方向：数据从输入流向输出（穿过高级策略），源码依赖全部指向高级策略
——两张图各走各的。

## 对照本项目

**"层"和"级别"方向相反**（易埋的雷）：

```text
调用顺序：  handler → service → domain ← repository
级别：        低        较高      最高       低
```

调用链的"上游"恰是级别的"低处"——handler 只是搬运工（解析请求、递交、格式化响应）。
目录排成一列易误读为楼层，实际是**两头低中间高的拱形**，依赖箭头全部向拱顶爬坡：
handler import service（低→高 ✓）、repository 实现 service/domain 声明的接口（低→高 ✓）。

一秒自测：**看包的 import 有没有圈口词汇**——有 gin/net/http 的贴 HTTP 口，
有 mongo-driver 的贴数据库口；什么都没有、只有纯业务类型的是高级策略。
domain/hmd 的杂质（bson.ObjectID、errcode）用本章语言描述：圈口词汇渗进了
离圈口最远的地方。

## 讨论沉淀（2026-07）

### 为什么级别按 I/O 距离定、低必须依赖高——完整论证

前提（已立）：架构度量 = 变更价格（ch15）；变更沿源码依赖边逆向传播（ch11）。
推论：**依赖箭头的终点是避风港**。什么配住进去？三个不对称：

1. **变化源可控性**：每个圈口对面站着不受你控制的变化源（小程序规范、DB 厂商、
   AI 迭代）；业务规则的变化源是你自己——系统里唯一自主的。"离 I/O 距离"是
   "离不可控变化源距离"的客观代理（看 import 即可量，不用吵架）；
2. **波及的语义**（核心）：规则变→适配器跟着变 = 必要功，天经地义，任何架构省不掉；
   设备变→规则跟着变 = 荒谬波及，纯浪费。**箭头指向高级策略 = 只保留必要波及、
   物理消灭荒谬波及**——不是美学，是两种波及一个有意义一个没有，箭头方向是唯一
   能区分对待它们的开关；
3. **数量**：N 个 I/O 适配器共享 1 份业务规则（发房 HTTP/后台/投影共享 domain/hmd），
   把 1 放避风港是唯一不爆炸的排法。

反驳化解（"我的业务天天变，Mongo 十年不变"）：混淆了两种变——规则变更是需求本身
（必要功，架构消灭不了也不该消灭）；架构能消灭的只有耦合导致的连坐。比的不是谁变得勤，
是谁的变化产生**无意义的**连坐。**架构的胜负从来不在必要功上，在浪费的多少上。**

### Auth 中间件题的答案

- 中间件级别很低（import：gin + session.Store，两个圈口的守卫）——定性正确；
- 但 handler 并不依赖 auth 实现：解耦已存在，用的是**流水线 + context 数据传递**
  ——中间件把验好的 Principal 作为数据存进 context，handler 只认识数据形状
  （session.PrincipalFromContext）。两个工位零调用。**接口不是解耦的唯一工具**：
  本项目已展示三种边界形态——接口（AIResponder）、数据回执（HmdChange）、
  context 传值（Principal），共同点是两侧只共享"形状"不共享"实现"；
- 主考点：**认证（authN，你是谁——机制，低级，middleware）与授权（authZ，你能干什么
  ——策略，高级，domain/publishaccess + 角色管理）已正确拆开**。很多项目把数据权限
  判断塞进中间件（业务规则住进 gin 依赖），本项目可当正面教材。
  RequirePermission 的比对动作是机制（放中间件对），权限码与路由的绑定表写在
  路由注册处——策略绑到传输层，恰是适配器本职。
