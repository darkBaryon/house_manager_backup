# 第 15 章 架构是什么？（What Is Architecture?)

## 本章讲什么

两个反直觉论断：

**一、架构的目的不是"让系统能跑"**——烂架构的系统照样跑。架构服务全生命周期
（开发/部署/运维/维护），终极度量只有一个：

> 满足需求所需的人力成本，随系统生命周期保持最小。**架构的好坏 = 变更的价格。**

优先级排序里"运维（性能）"最低：硬件比人力便宜，慢能买机器解决，改不动买不来。

**二、好架构师最大化"未做决策"的数量。**系统 = 策略（业务规则）+ 细节（DB、框架、
协议）。让细节的决策可推迟：拖得越久信息越多选得越准，"还没决定"意味着随时能换。

## 对照本项目

- 度量的切身对照：前身 Python ai_house 能跑，重写的原因是**改不动**——
  变更价格涨到受不了。触发重写的从来不是跑不动。
- **推迟成功的决策**：AI 供应商（AIResponder 后随时换）、投影同步/异步
  （listingProjectionApplier 插座留给 outbox）、Redis（cache.Client 接口 +
  RedisAdapter，service 层仅 chat RuntimeContextStore 一处摸到具体类型）、
  Gin（54 个文件 import，但全部在 handler/middleware/app/response 外圈，
  service/domain 零渗透，gin.Context 止步 handler）。
- **焊死的决策只有 Mongo**：bson.ObjectID 进了 domain 接口签名、model 就是 bson
  struct。不是"做了"这个决策，是焊死了。

## 讨论沉淀（2026-07）

### diff 大小 ≠ 渗透深度

- 换 Gin：diff 最大（54 文件），渗透最浅（全在适配层，书允许框架拥有外圈）；
- 换 Redis：diff 最小，渗透最浅——双料模范；
- 换 Mongo：diff 最大且渗透最深——**"深"的定义 = 越过适配层进了策略层**。

判断口诀：**评估技术选型绑得多死，别数 import 它的文件数，看它的类型出现在
哪一层的函数签名里。签名是合同，import 只是认识。**

### Mongo 渗透的精确解剖

model 层的"满身 Mongo"要分三样：bson struct tag（无害，纯字符串不产生 import）、
repository 调 driver（天经地义，这层本来就为换库时整层重写准备）、
**bson.ObjectID 类型（真正的元凶）**——"实体的身份标识"这个业务概念被数据库厂商
类型表达，扩散到全项目签名。

三档解法与价目表（可逆性有价格）：
1. 教科书：纯净实体 + 持久化模型 + 双向 mapper——月租最贵（字段涟漪每层加一站），不推荐；
2. **便宜解法：`type ID = bson.ObjectID` 别名收口**——物理耦合还在，但"Mongo 的名字"
   从几百处签名收缩到一行；换库那天改一行 + 让编译错列清单。不付抽象税，只买逃生通道；
3. 不解：承认"ID 就是 ObjectID"是赌注的一部分。

**本项目判决：现状保持（追缴不划算），"便宜解法"记入下个项目第一天清单**
（成本为零的时机做才是白赚）。

### 公道话

"最大化未做决策"有成本（可推迟性 = 抽象层 = 真金白银工作量）。单人、明确不换库，
焊死 Mongo 换来全程无抽象税可能是好交易。**"我焊死 Mongo，赌它陪我到底"是架构决策；
"没想过这个问题"才是架构失职。**
